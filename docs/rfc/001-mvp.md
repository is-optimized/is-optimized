# RFC-001: is-optimized.com MVP

| Metadata | Decision |
| --- | --- |
| Status | Proposed; revised following owner clarification |
| Product | is-optimized.com |
| Company | Sire Run, Inc. |
| Runtime | Go application on Nanos unikernel, hosted on GCP Compute Engine |
| Purpose | Free, useful website readiness reports that introduce Sire Run, Inc. to prospective customers |

## 1. Product and scope

A visitor arriving from a social group enters a domain and receives a compact scorecard for SEO, GEO, and AI-agent readiness. The complete report explains the evidence, prioritized fixes, and instructions the visitor can give a developer or coding agent. It is available as both a shareable HTML page and a printable PDF generated from the same report model.

The prominent action is **Text me the report**. It opens a pre-filled message in the visitor's messaging application. After the visitor sends it, Twilio delivers the inbound message to this service, which replies with a link to the PDF. The alternative action, **View report online**, opens the complete HTML report without requiring a phone number or marketing consent.

This MVP generates reports, records the supplied consent choices and their evidence, and sends requested report links. It does not run marketing campaigns, make calls, or operate a CRM. David will supply the approved disclosure and pre-filled message wording. This RFC specifies implementation behavior, not a legal conclusion about that wording.

### Fixed decisions

- Entire application in Go, with minimal dependencies and one application process per Nanos instance. No Node runtime, external CLI, headless browser, or subprocess in production.
- Reimplement relevant `is-agentic` checks in Go; add SEO and GEO checks.
- Scan the homepage and at most four distinct pages linked directly from it, on the same site. Fetch those additional pages concurrently with bounded goroutines. Never recursively crawl them.
- Keep all three pillars, compact initial scores, and complete HTML/PDF remediation reports.
- Marketing consent is optional. Declining it does not remove access to the complete report.
- Twilio handles SMS transport. Outbound marketing and shared suppression across calls and texts are deferred.
- Low memory consumption, millisecond-scale boot, and fast scans are performance goals to benchmark, not established results.

## 2. Visitor journey

1. **Enter domain.** Normalize a bare domain to an HTTPS homepage URL. Reject credentials, non-web schemes, unsupported ports, and private destinations. Explain invalid or unreachable targets without inventing scores.
2. **Scan or reuse.** Reuse a compatible completed report within its cache lifetime; otherwise create or join one bounded scan. Display progress while it runs.
3. **Preview.** Show three pillar scores, scan timestamp, page coverage, and an explicit incomplete state when evidence is insufficient. Avoid implying the entire website was audited.
4. **Choose delivery.** Present a prominent Text me the report action and an accessible View report online alternative. Neither action silently grants marketing permission.
5. **Read and share.** The HTML report has a stable domain route such as `/example.com`; each completed report also has an immutable version URL. The PDF and versioned HTML identify the same scan, methodology version, and findings.

### SMS handoff

Create a short-lived, unguessable request token tied to the report version and disclosure version. Put that token in the pre-filled SMS along with owner-supplied wording. Opening the composer is not sending a message and must not create a completed delivery or consent event.

Use the authenticated inbound Twilio message's sender as the delivery destination. An optional typed phone number is not proof that the visitor controls it. Match the request token, validate the expected message action, persist the inbound provider ID, and create one reply intent. The reply contains a report link; do not attach the PDF as an MMS requirement.

On devices without a usable SMS composer, show the destination number and message for manual sending, alongside the HTML alternative. Expired, altered, or unrecognized request messages do not create marketing permission. Keep report-delivery requests and marketing choices as separate records; the final permitted consent action depends on the wording David supplies.

## 3. Scan boundary and evidence

### Page selection

Resolve robots policy before fetching content, including at each redirected origin. A missing robots file (404/410) permits scanning; unavailable, oversized, or malformed policy makes affected content unobserved. Policy requests consume the discovery and total request budgets. Then fetch the homepage. Extract HTTP(S) links from that response, normalize fragments and duplicate URLs, and select at most four same-origin HTML page candidates in deterministic document order. Exclude logout/action links, query-bearing URLs, downloads, mail links, and telephone links. Record the selection policy version and selected URLs. A future explicit policy can prioritize page types without silently changing historical scores.

The final validated homepage origin defines the site boundary. Redirects on candidate pages must remain within that origin. Homepage redirects to another public origin are allowed only after complete destination validation. If fewer than four eligible links exist, scan fewer pages; this is not itself a failure. Additional-page failures remain visible rather than triggering unbounded replacement crawling.

Fetch the four selected pages concurrently, with a per-scan concurrency cap of four and a separate global cap. All requests, including discovery probes, share the global budget.

### Discovery probes

The five-page cap covers content pages. Separately allow a small, explicit probe budget for `robots.txt`, a declared sitemap, and relevant machine-readable discovery files. Do not recursively enumerate sitemap contents or fetch all their URLs. Do not execute forms, authenticate, invoke MCP tools, introspect arbitrary APIs, or perform transactions. Schema or endpoint presence alone does not demonstrate that an agent can use it.

Proposed initial limits, configurable and verified in load tests:

| Limit | Initial value |
| --- | --- |
| Content pages | 5 total, depth one |
| Discovery requests | 8 maximum |
| Redirects | 3 per request, charged to a 32-request total budget |
| Decompressed response size | 2 MiB per response |
| Total decoded bytes | 12 MiB per scan |
| Request timeout | 5 seconds |
| Overall scan deadline | 15 seconds |
| Concurrent scans per instance | 4 initially |

Truncation, timeout, denied access, and parser errors produce explicit unknown results. A successful HTTP response containing an app shell is not evidence of the rendered application. JavaScript rendering and observed agent tasks are outside the MVP.

## 4. Checks and scoring

Scores describe observed technical signals. They do not predict rankings, guarantee AI citations, establish authority, or prove transaction success. Label the third pillar **AI-agent readiness (AEO)** and define that usage explicitly; do not conflate it with answer-engine optimization.

### Pillars

| Pillar | Proposed check groups | Limits of interpretation |
| --- | --- | --- |
| SEO | Fetch/index directives and canonicals; titles/descriptions; headings and semantic structure; image alternatives and link labels; sitemap signals; viewport and observed response behavior | Sample coverage only. Network timing is a measurement from this scanner, not field performance or Core Web Vitals. |
| GEO | Structured entity data; authorship and dated content where applicable; citations and extractable information; crawler-policy observations | Structured data is not verified truth. Different crawler tokens have different purposes; training opt-outs must not automatically lower a discovery score. |
| AI-agent readiness | Initial HTML readability; meaningful navigation and controls; discoverable policies; conditional API documentation; emerging machine-readable content conventions | Static evidence cannot prove interaction, authentication, or task completion. Missing APIs do not penalize a site without an applicable API surface. |

Do not treat one heading count, a fixed answer length, TLS version preference, or a particular social profile as a universal quality requirement. Emerging conventions such as `llms.txt` are informational until their exact check and weight are justified. Do not describe a guessed well-known MCP path as a universal standard.

### Methodology contract

Every check has a stable ID, pillar, applicability predicate, weight, pass/partial/fail rule, evidence requirements, remediation template, and methodology version. The complete check registry is an implementation deliverable required before public scoring. No unreviewed heuristic receives a production weight.

Proposed scoring rule: pass earns 1, partial earns 0.5, fail earns 0. Each pillar score is `100 * earned_weight / observed_applicable_weight`. Not-applicable checks are excluded with a reason. Unknown checks contribute to coverage, not observed weight. Coverage is `observed_applicable_weight / total_applicable_weight`; withhold a numeric pillar score below 80% coverage or when a required foundational check is unknown. Display coverage beside every published score. If the denominator is zero, report insufficient evidence.

The three pillar scores are the primary product output. Defer a composite score and bonus points until the registry is calibrated; the draft's 30/35/35 and 80/20/+5 formulas were not a single consistent methodology. Preserve methodology versions in cache keys so changed scoring never masquerades as a website change.

### Upstream reference

The npm metadata for `is-agentic@1.0.1` identifies the Vercel Labs repository and declares ISC for the CLI. Its README says the CLI retrieves stored reports or starts scans through the hosted service; the npm client is not itself evidence that the complete scanner is available locally.

Before porting, inspect and pin the relevant upstream source and license, identify the actual checks, and document which are reimplemented, modified, or omitted. Preserve required notices. Do not claim exact scoring parity without fixture comparisons. Production must perform its own Go probes and must not depend on the upstream hosted scan API.

Reference: [is-agentic source](https://github.com/vercel-labs/is-agentic), [documentation](https://is-agentic.com/docs).

## 5. Shared HTML and PDF report

Generate both formats from one immutable `Report` object containing target, selected pages, timestamps, scanner/methodology versions, pillar scores and coverage, findings, evidence, and remediation. Rendering must not rescan or recompute scores independently.

The report includes:

1. Executive scorecard and exact scan coverage.
2. Prioritized findings, each with observed evidence, affected URL, impact, and a concrete fix.
3. Pillar detail, including unknown and not-applicable checks.
4. Coding-agent instructions grounded in those findings, with validation steps and a request to inspect the actual code before editing.
5. Relevant starter snippets, clearly marked as drafts requiring factual verification.
6. Sire Run, Inc. branding and an optional service CTA.

Use readable typography and print-safe contrast, retaining the draft's ivory, charcoal, and muted cyan direction. Let content determine pagination; promise neither seven nor twelve fixed pages. HTML must be responsive and accessible, and PDF text must be selectable with working links and embedded fonts. Select one maintained pure-Go PDF library after a small rendering check; keep that dependency behind an interface.

Treat fetched text as untrusted data. Escape HTML, bound evidence excerpts, and prevent page content from becoming instructions in generated coding-agent prompts. No LLM is required for MVP report generation; use deterministic templates.

Reports are shareable public-site assessments. Public HTML/PDF contains no phone numbers, consent records, delivery tokens, or internal logs. The stable domain route shows the latest completed snapshot, with its age; immutable report URLs preserve prior versions until expiry. Use unambiguous reserved API/report route prefixes and a validated domain route. Set reports to noindex initially to avoid creating a search-indexed duplicate-content directory.

## 6. Go/Nanos architecture

Use Go's standard library where practical: HTTP server/client, TLS, JSON, templates, concurrency, cryptography, and structured logging. Justified dependencies include an HTML parser, a pure-Go PDF renderer, and maintained cloud/authentication libraries where they avoid hand-written security protocols. Minimal dependencies means a reviewed dependency budget, not custom cryptography.

Embed the frontend, templates, fonts, and static assets in the binary. Package the application with a pinned Nanos/OPS toolchain. Qualify DNS, TLS roots, clocks, cloud authentication, storage clients, and PDF generation in the actual GCP Nanos image early. A successful Linux build is not runtime qualification.

[Nanos documentation](https://nanos.org/faq) describes Go and Google Cloud support; [OPS documentation](https://docs.ops.city/ops) describes packaging and orchestration. Those capabilities do not establish this application's boot time or compatibility with its selected libraries.

### Persistence and recovery

Retain Firestore for durable reports, scan jobs, delivery requests, and consent events, and GCS for PDF artifacts. Start with a small bounded in-memory cache rather than adding a separate cache library or service. Proposed TTLs: one hour in memory, 24 hours for scan reuse, 30 days for report artifacts. Consent/delivery retention is a separate policy to be supplied before production collection; report expiry must not silently determine it.

Use one Firestore-backed job state machine owned by this service: queued, running, completed, partial, failed. Workers acquire expiring leases transactionally, with a generation token checked when publishing results. A bounded in-process dispatcher recovers expired work after restart; do not add a second scheduler. Limit queue depth and reject overload before accepting unlimited jobs.

Write PDF artifacts under an immutable report ID, then atomically publish the completed report pointer. An interrupted artifact write must not publish a broken link. If PDF generation fails, keep the scan evidence and expose a retryable rendering state; do not rescan the website to regenerate a PDF.

Persist SMS intents before sending and deduplicate inbound events by Twilio message ID. Atomically consume each request token, bind it to the authenticated sender, and create a reply intent uniquely keyed by that request in the same transaction. Further messages using that token return the recorded result without another send, even if their provider IDs differ. Track pending, sending, accepted, delivered, failed, suppressed, and outcome-unknown states. Provider acceptance is not delivery. If a crash or timeout makes the send result uncertain, reconcile using provider evidence; never blindly retry and risk duplicate texts.

### Hosting and edge

Proposed baseline: a GCP HTTPS load balancer with managed TLS in front of replaceable Nanos instances, deployed through repository-owned IaC. Start with one instance if launch budget requires it, explicitly accepting interruption during replacement; use two across zones when continuous availability is required. Durable state remains outside instances in either case.

Cloudflare is optional and is not required by this RFC. A unikernel reduces host surface but does not provide application rate limiting or traffic-abuse controls. Implement bounded admission in Go regardless of edge choice. Select the final edge topology and instance count with a cost estimate before deployment, without changing the product scope.

Use workload identity/service-account credentials with least privilege; do not embed Twilio credentials or cloud keys in images or checked-in configuration. Qualify secure secret retrieval on Nanos. The scanner transport must never access cloud metadata; a separately controlled credential client may use the approved platform mechanism.

All resource identities remain deployment inputs. The old `sire-run-prod` names and guessed CRM endpoint are not confirmed resources or authorization to deploy. Use Pulumi or the repository's established IaC, review the preview, and deploy only under separate authorization.

## 7. Security and SMS boundaries

### Fetch safety

All target-controlled outbound requests use one hardened transport. Resolve and validate every destination and redirect; reject all non-public IPv4/IPv6 ranges, mapped-address bypasses, loopback, link-local, metadata, and internal names. Dial only the validated address while retaining correct TLS hostname verification. Do not permit DNS rebinding, environment proxy bypasses, URL credentials, arbitrary ports, or target-controlled access to provider clients.

Apply byte limits after decompression, parser limits, connection limits, request deadlines, and total scan budgets. Bound redirects and discovery fetches. Identify the scanner and respect applicable robots rules; a disallowed fetch becomes unobserved rather than a claimed failure of the site. No authenticated scans or user-submitted cookies.

### Application safety

Apply global, per-client, and per-domain admission limits, with persistent delivery throttles across instance restarts. Trust forwarded IP headers only from the configured ingress. Protect against scan amplification, SMS pumping, duplicate requests, and token guessing. Limit request bodies and sanitize logs. Public report retrieval must not trigger a new scan or send.

Verify Twilio webhook signatures against the configured public URL, validate account/sender context, deduplicate callbacks, and keep secrets out of logs. Browser data cannot impersonate an inbound SMS.

### Consent and STOP

Store versioned disclosure text, the explicit choice/action, relevant timestamps, request token linkage, and inbound provider evidence separately from the public report. Do not call an SMS request cryptographic proof of legal consent. Exact language and retention policy remain owner-supplied launch inputs.

Configure Twilio's supported opt-out handling and respect suppression errors. STOP/HELP messages must not be interpreted as report requests, and a blocked send must not be retried through another sender. With Advanced Opt-Out configured, Twilio can supply `OptOutType` in the inbound webhook; record that provider event where available. See [Twilio opt-out event documentation](https://help.twilio.com/articles/31560110671259-How-to-Track-Opt-Out-Opt-In-and-Help-Messages-Using-the-OptOutType-Parameter).

A shared company-wide do-not-text-or-call list, cross-channel enforcement, and its owner are explicitly deferred. Twilio sender-level behavior does not establish company-wide voice suppression. No marketing or calling capability is introduced by this MVP; designate that owner and qualify suppression before adding those capabilities.

## 8. Internal contracts and repository layout

Suggested endpoints:

| Endpoint | Responsibility |
| --- | --- |
| `POST /api/v1/scans` | Validate domain, reuse snapshot or admit one scan; return ID/status |
| `GET /api/v1/scans/{id}` | Return bounded progress or completed scorecard |
| `GET /{domain}` | Latest completed HTML report |
| `GET /reports/{id}` | Immutable HTML report version |
| `GET /reports/{id}/pdf` | Serve or redirect to matching PDF artifact |
| `POST /api/v1/report-requests` | Create expiring SMS handoff token and versioned consent context |
| `POST /webhooks/twilio/inbound` | Verify and persist inbound message; create at most one reply intent |
| `POST /webhooks/twilio/status` | Verify and reconcile delivery status |

Use opaque IDs, explicit status/error schemas, and API versioning. Expired artifacts return a clear expired state and a separate rescan action; public GET requests never perform expensive or messaging effects.

```text
cmd/server/          HTTP service and bounded dispatch loops
internal/scanner/    Safe fetcher, page selection, probe orchestration
internal/checks/     Versioned SEO, GEO, and agent-readiness registry
internal/scoring/    Applicability, coverage, deterministic scores
internal/report/     Shared report model, HTML and PDF renderers
internal/store/      Firestore/GCS persistence and lease transitions
internal/messaging/  Twilio validation, intents, delivery reconciliation
web/                 Embedded UI, fonts, templates, static assets
infra/               IaC and pinned Nanos image packaging configuration
```

## 9. Delivery and acceptance

These are implementation stages, not promises that work is already complete. Estimate effort after the first runtime and check-inventory work.

| Stage | Required acceptance evidence |
| --- | --- |
| Runtime slice | Actual Nanos/GCP image serves HTTPS through chosen ingress, uses approved identity, reads/writes durable state, and renders a PDF. Record versions and measured resource use. |
| Scanner and registry | Tests prove depth-one five-page cap, deterministic selection, bounded concurrency, redirect/SSRF protection, timeout handling, and unknown/applicability scoring. Pin and review upstream methodology mapping. |
| Report experience | One scan produces equivalent HTML/PDF findings and scores; mobile layout, printable PDF, links, accessibility, and incomplete-report states reviewed with fixtures. |
| SMS slice | On approved test numbers, composer/manual flow leads to an authenticated inbound event and one report-link reply. Test duplicates, expired tokens, provider outage, uncertain outcome, and STOP suppression. |
| Recovery and release | Restart during scanning, artifact generation, and delivery cannot publish inconsistent reports or blindly duplicate sends. Load-test admission and memory bounds. Review IaC preview and separately authorize deployment. |

Benchmark separately: kernel boot to application readiness, cloud provisioning to reachable service, cached response latency, uncached five-page scan latency, PDF render time, peak memory, image size, and cost per completed report. Record p50/p95 under a declared workload and instance shape. The aspiration is millisecond-scale boot and a responsive experience; no fixed millisecond or sub-four-second claim is accepted without measurements.

## 10. Remaining launch inputs

Product scope is settled. The following do not block this RFC rewrite but must be resolved at their implementation or release gate:

- David's approved disclosure and pre-filled SMS wording, with exact consent recording behavior.
- Twilio account, sender configuration, test numbers, and verified webhook setup.
- Upstream check inventory/source/license review and calibrated check registry.
- GCP resource identities, region, budget, edge topology, instance count, and secret access.
- Consent/delivery retention policy and access controls.
- Runtime compatibility, resource benchmarks, and acceptance evidence.

Deferred: recursive crawling, JavaScript rendering, observed agent tasks, LLM-generated findings, outbound campaigns/calls, CRM integration, and company-wide suppression ownership.
